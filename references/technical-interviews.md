# 技术岗位路径

仅在目标为技术岗位时读取；产品经理路径使用独立参考文件。沿用 SKILL.md 的逐点覆盖、全部追问有答案、事实边界与本地网页要求，题库设置 `track: technical`。

## 轮次矩阵

| 轮次 | 要验证的能力 | 提问路径 | 希望取得的证据 |
| --- | --- | --- | --- |
| 技术一面 | 项目真实性、实现深度、相关基础 | 一次真实请求的全链路 → 关键数据或状态 → 设计原因 → 具体故障 → 效果验证 → 本人贡献 | 可还原的执行过程、代码或数据细节、真实决策和排障案例 |
| 技术二面 | 从零设计、工程化和取舍 | 目标与约束 → 最小方案 → 逐次增加失败、规模、权限或成本约束 → 比较方案 → 验证 | 状态边界、恢复和一致性、容量估算、方案代价、验收方法 |
| 负责人／CTO 轮 | 个人判断、经验迁移和独立交付 | 选择动机 → 已有行动与结果 → 关键个人决策 → 新业务验证 → 交付计划 | 有依据的判断、主动性、优先级、业务指标和承担结果的方式 |

这些是练习视角，不是任何公司的固定流程。负责人经历突出架构决策、跨团队推进与结果；执行岗位重视本人实现和定位问题的深度。相关基础、编码、调试或计算题按目标岗位需要纳入。

## 逐轮追问

- 一面沿同一事实深入：做过什么 → 为什么做 → 具体如何运行 → 出过什么问题 → 如何定位并证明修复。追问落在可解释的数据、状态或决策上。
- 二面先给清楚场景，再一次改变一个条件。先明确发生了什么、已经产生什么副作用，再讨论恢复、重试、降级或重新规划，避免只问组件名称。
- 负责人轮先要实例，再听观点和计划。“关注哪些新闻”继续追问实验与决策变化；“有什么优势”继续追问案例；“有没有信心”继续追问目标、依据、资源和阶段验收。
- 同一技术点跨轮次改变验证目标：过去怎么实现 → 新约束下怎么设计 → 为什么值得投入。估算要列假设，设计要说明代价，不设唯一架构关键词答案。
