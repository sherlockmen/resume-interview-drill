# 产品经理路径

仅在目标为产品经理时读取。题库设置 `track: product`，独立建立事实清单、题号、轮次、覆盖表、缺口和网页。遵守 SKILL.md 的所有信息点覆盖、每条追问有答案、事实边界与隐私要求；不混入技术岗位题库，不默认称负责人轮为 CTO 轮。

## 提问主线

目标与用户 → 问题证据 → 备选方案 → 优先级与取舍 → 推进落地 → 指标与效果归因 → 失败复盘 → 换场景迁移。

先找一个具体事件，再沿同一事件取证。每一问写出考察目的和期望证据，每次追问只推进一个判断。框架名称只能帮助组织推理，不能代替用户、动作、决策和数据。

## 轮次矩阵

以下三轮用于编排练习，不代表公司的固定流程。按实际 JD、资历和已知流程调整；同一能力可能在多轮出现，但应改变追问目标。

| 轮次／网页名称 | 重点问题 | 追问方式 | 好答案需要的证据 |
| --- | --- | --- | --- |
| 产品一面／经历复盘 | 做了什么产品、服务谁、解决什么问题、怎么发现、自己负责哪一步 | 以具体需求或项目为入口 → 还原触发背景 → 核对调研和需求依据 → 方案形成 → 本人动作 → 交付与复盘 | 可还原的工作过程、来源与样本限制、决策材料、个人与团队分工；写 PRD 不等于决定方向 |
| 产品二面／产品分析 | 为什么做它、为什么先做、还有什么方案、怎么证明有效 | 先核对已有判断，再一次改变预算、期限、人群、资源或数据条件 → 比较机会成本 → 提出验证与停止条件 | 备选方案、可解释的排序、指标口径、反证、异常解释、验证方法与不确定性 |
| 产品负责人轮／业务判断 | 为什么值得投入、定位与商业价值、资源如何分配、如何影响他人 | 从过去实例进入 → 客户与付费方 → 竞争和替代方式 → 投入产出 → 路线图 → 协同和阶段决策 | 用户与业务目标的联系、可承担的责任、资源约束、明确优先级、阶段验收与退出条件；不要求初级岗位虚构经营责任 |

## 逐点覆盖怎么做

- 将材料里的背景、教育、每段任职、每个项目、用户与客户、功能、分析方法、协作、工具、成果和岗位变化拆成原子点，逐一映射到具体问题与答案。不得只覆盖“最有代表性的项目”。
- 每个项目至少覆盖：问题与目标、用户与场景、需求证据、本人职责、关键方案及取舍、推进过程、结果口径、失败或限制。材料未写的经历仍可提出核实问题，但答案必须标待补；情景推演另标假设。
- “用户调研”追样本来源、对象选择、访谈或观察过程、结论如何改变方案以及偏差；“需求分析”追业务目标、真实问题与方案请求的区别；“原型／PRD”追状态、异常、规则与验收，不止问画图工具。
- “数据分析／SQL”等技能先问实际用于什么判断、输入是什么、输出如何核验；是否增加查询编写题由 JD 决定。“沟通能力”要具体分歧、各方目标、本人动作及结果；“主导”要核对决策权与协作者贡献。
- 数字成果逐项核对口径和归因；教育、证书、领域经历、转岗及空档等背景点也要有具体问题与诚实回答，避免无关的隐私探问。

## 不同题型怎么问、怎么答

| 题型 | 提问顺序 | 回答要求 |
| --- | --- | --- |
| 项目／行为复盘 | 发生了什么 → 你为何这样判断 → 具体做了什么 → 谁做了其余部分 → 结果与复盘 | 真实目标、个人角色、动作、决策、结果证据与限制；不能把团队成果全归个人 |
| 产品设计／改进 | 明确目标 → 用户分层和场景 → 关键问题及证据 → 方案比较 → 最小范围 → 验证 | 使用“我会”，区分已知条件与假设；说明不做什么、异常与可用性，不能直接罗列功能 |
| 指标异动／效果评估 | 确认口径与数据质量 → 拆人群、渠道、阶段与时间 → 提出解释 → 找区分证据 → 决策 | 区分相关和因果，避免看到指标下降就直接改功能；说明下一步用什么证据排除哪个解释 |
| 优先级／资源冲突 | 对齐目标与硬约束 → 比较影响、成本、风险和依赖 → 说明排序 → 缩减范围 → 验证 | 排序分数不是事实；标清估计依据与信心，不伪造 RICE 等模型输入；解释被推迟需求的代价 |
| 产品拆解／竞品／商业判断 | 目标用户与任务 → 现有替代方式 → 关键差异 → 商业机制与约束 → 可检验机会 | 区分公开信息、亲自观察与推断；比较真实使用场景，不背优缺点清单；当前产品事实需核验 |
| 估算／冷启动 | 明确对象与范围 → 分解变量 → 给出假设与区间 → 敏感性 → 低成本验证 | 列单位、时间、人群、分母；示例数字明确为假设，不冒充调研结论 |

主答先给可口述版本，再在 `details` 补分析、计算或验证步骤。材料不足时给已知事实版本及 `【待补充：具体字段】`，不能用“按 STAR 作答”代替答案。历史失败不能现编；可以诚实说明未有记录，再另答标明假设的应对方案。

## 连续追问示范

以“优化过一个需求”为主问，按证据递进选择追问，不必机械地全部重复：

1. 怎么确定这是真问题？——验证需求来源、人群和证据限制。
2. 为什么先做它？——核对目标、优先级、机会成本。
3. 还有什么方案？——检查取舍，允许暂缓或不做功能。
4. 你具体推动了哪一步？——分清个人动作、决策权和团队贡献。
5. 效果怎么算？——核对指标定义、基线和统计范围。
6. 如何排除渠道、季节或同期活动影响？——检查归因，而非默认成果由方案造成。
7. 重做会删掉什么？——检查复盘是否真的改变判断。

这只是提问顺序示范。实际生成时，所有列出的主问及追问都要根据材料填写答案；不能照搬此处的验证说明作为回答。核心问题通常挑选 2—4 个有新增证据价值的追问。

二面应将新条件写成清楚的假设，例如：“上线后主指标没变化，但投诉增加；先查什么？”继续追“哪一项证据会改变你的判断”，不要只索要分析框架。负责人轮先要过去的具体实例，再讨论新的投入与计划。

## 指标与归因的硬要求

- 每个成果明确：指标定义、分子分母、时间窗、样本／人群、基线、数据来源和护栏。百分比区分相对提升与百分点；累计量不能替代同期增量。
- 上线前后变化只说明观察结果。没有对照或合理识别方法时，明确外部因素与证据能支持到哪一步，不直接宣称方案“带来”全部提升。
- 如果实际做过实验，核对分流单位、样本选择、实验窗口、主指标、护栏和判定依据；干扰、选择偏差与过早停止等按具体场景追问。未做过实验不得补写 A/B 经历，也不能给无依据的显著性结论。
- 没有数值就用变量或明确的假设示例，列出待补字段。用户价值、采用／留存等过程指标与收入／成本等结果指标分开，不把交付上线直接写成商业成功。

## 按岗位追加的重点

只加载与 JD 或材料相关的分支；通用的逐点覆盖不因此缩小。

- **C 端／增长：** 用户分层、使用动机、关键路径、激活留存、渠道质量和体验护栏；追增长来自新增、回流还是结构变化，以及是否透支长期价值。
- **B 端／平台：** 购买方、使用方、管理方的差异，业务流程与权限规则、异常和交接，标准化与定制取舍，交付、采用与业务效益；上线不等于客户真正使用。
- **AI 产品：** 先问是否需要 AI、规则或人工替代方案，再追可接受错误、评测集来源与授权、离线评测和真实任务效果、成本／时延、人工接管和反馈闭环。技术只深入到支撑产品判断的程度，不默认转成模型训练或分布式系统考试；JD 明确要求的技术能力仍须涉及。
- **资深／负责人：** 定位、竞争、商业机制、资源组合、路线图和组织协同，追停止条件与承担结果的方式。初级或转岗岗位可用明确标记的情景题验证潜力，不虚构收入责任或管理经历。
